# Changelog

## 0.1.0

Minor release: the first release, a new surface of three crates (`forgr-schema`, `forgr-macros` and `forgr`) with no earlier version to break. forgr keeps no schema of its own: it reads an app's schema.json and never writes it, so there is no schema migration. Every crate declares `rust-version = "1.89"`. forgr depends on rusqlite 0.41 with SQLite bundled, and libsqlite3-sys links `sqlite3`, so only one version of it can be in a build: an app that uses rusqlite anywhere in its graph must be on rusqlite 0.41 (libsqlite3-sys 0.39) to add forgr.

The first release. forgr makes test data from the schema.json an app already has, in migratr's format, with no database file. One call, `forgr::schema!("<path>/schema.json")`, gives a module per table and an empty in-memory test store built from that schema with foreign keys on. Each table's module has a factory with a typed setter per column, where leaving a required column unset is a compile error naming it. With the `fake` feature, each module also has a mock that writes any number of rows, makes a parent row for each required foreign key, and takes per-column overrides. The same call emits a test that prepares the SQL in every workspace crate against the schema, so a query naming a column the schema lacks fails `cargo test`. Because the macro includes schema.json, a change to that file alone rebuilds the call, and a renamed column then fails the build at every place a test still uses the old name.

### New
- **`forgr-schema` reads schema.json by replaying it** (PR #13, #2; PR #15, #4): `Schema::read(text)` parses schema.json in migratr's format, whoever wrote it, and replays it into an in-memory SQLite, tables first. Each virtual table is created by its own `CREATE VIRTUAL TABLE`, and the file's entries for its shadow tables are skipped. The model is then read from what SQLite reports: each table's columns, primary key and foreign keys by PRAGMA, and each `CHECK (col IN (...))` list from the `CREATE TABLE` text. `Schema.tables` keeps file order and leaves out virtual tables and their shadow tables. `forgr_schema::replay(text)` returns the replayed store itself as a `rusqlite::Connection`. Neither function writes the file or opens a database file. A failure is an `Error` that says which: `Parse` (where the text is not migratr's format), `Open`, `Replay` (naming the object's kind and name) or `Read` (naming the table). forgr-schema depends on no proc-macro crate, so schema.json is parsed through `serde_json::Value` and `Error`'s `Display` is written by hand. A schema.json written by hand and one written by migratr 0.3's `write_schema` from the same store differ only in key order, and both read to the same model of 91 tables (PR #22, #11).
- **`schema!` gives a module per table and the empty test store** (PR #14, #3; PR #15, #4): `forgr::schema!("<path>/schema.json")` takes a path relative to the calling crate's manifest directory and puts its items into the scope where it is called, so it is called inside a module. It emits one module per table, plus `empty_store()`. `empty_store()` returns a fresh in-memory connection replayed from schema.json by `forgr_schema::replay`, with no rows and with foreign keys on, so a row whose foreign key names no parent is refused. The generated code names only `::forgr::` paths, so the calling crate needs no rusqlite dependency of its own. The macro emits `include_str!` of schema.json, so an edit to that file alone expands the call again, and forgr never changes the file.
- **Table factories with typed setters** (PR #16, #5; PR #20, #9): each table's module has `factory()`, a column marker per column in `col`, and `Row`. A factory starts empty and is set with a chained setter per column, typed by the column's SQLite affinity. A column whose name is a Rust keyword gets a raw identifier, such as `r#type`. Every required column (NOT NULL with no default, or part of the primary key) is a type parameter of the factory, and `insert` requires each one to be set. A required column left unset fails to compile with `error[E0277]: a required column was never set: <table>::col::<column>`. `insert(&store)` writes the row with `INSERT ... RETURNING` and returns it as the module's `Row`, with defaults and keys included, so a column left unset gets the schema's default. A factory can attach a child to an existing parent by setting the foreign-key column, and an events table gets a factory like any other table. An FTS5 table gets no module, so calling its `factory()` fails to compile.
- **Table mocks behind the `fake` feature** (PR #17, #6; PR #18, #7; PR #19, #8; PR #20, #9): with forgr's `fake` feature on, each table's module has `mock(n)`. `n` is a count, or a Rust range from which a count is drawn at random: `mock(3..32)` writes 3 to 31 rows, and `mock(3..=32)` writes 3 to 32. `insert(&store)` writes the rows and returns them as written, keys included. A mock gives a TEXT primary key a UUIDv7 and an INTEGER one a random positive integer, and it gives a column with a `CHECK (col IN (...))` list one of the listed values, including a TEXT key column with such a list. A column with a default is left to it. A nullable column is NULL in some rows, and a nullable foreign key is NULL. Made-up text is a word with a random suffix, so a UNIQUE column takes every row. For each required foreign key to another table, the mock makes a fresh parent per row through that table's own mock and sets the key from the parent's referenced columns, composite keys included. A key that names no column references the parent's primary key. A required foreign key to the table's own table gets no parent, so the test sets it, for example with `Fixed`. `mock(n).with(Overrides { .. })` sets what the mock writes to a column. Each field of the table's `Overrides` struct is an `Override`: `Fake` by default, `Fixed(value)`, `Pick(list)` or `Each(closure)`, and the closure is called per row with the row number and a `pick(list)` helper. `..Default::default()` leaves the remaining fields `Fake`. Overrides are applied after the parents are made, and a required foreign key the test overrides gets no fresh parent. `schema!` re-exports `Override` beside the table modules. Without the feature, calling `mock` fails to compile with `` error[E0277]: mocks need forgr's `fake` feature ``. An FTS5 table has no mock. Every one of the kessel schema's 91 tables mocks with no overrides, with no errors and no foreign-key violations.
- **The SQL check, `forgr_sql_matches_schema`** (PR #21, #10): `schema!` also emits a test in the crate that calls it. The test reads the workspace's members from `cargo metadata`, and takes the string literals in each member's non-test `src/` (read with syn) and each statement in its `.sql` files. It then prepares each one against the schema.json replay in memory. A statement that names something the schema lacks fails the test with its file and line, and the report counts checked, failed and unchecked statements separately. PRAGMA text counts as SQL. The check does not see everything. SQL built with `format!` is not supported in 0.1 and is listed as unchecked. DDL (CREATE, ALTER, DROP), in a literal or a `.sql` file, is listed as unchecked and never prepared. A string that looks like SQL but does not parse is listed as unchecked and never fails the test. `#[cfg(test)]` code, the files of `#[cfg(test)]` modules and a crate's `tests/` are not scanned. The README and the rustdoc on `schema!` give these limits.
- **One crate owns the schema, and other crates' tests use it** (PR #22, #11): this release's re-runs of the design toys confirm a pattern for a workspace. The owning crate calls `schema!` once, in its library, inside a module behind a cargo feature that turns on forgr as an optional dependency, for example `#[cfg(any(test, feature = "testing"))] pub mod forgr { forgr::schema!("schema/schema.json"); }`. Another crate's tests then reach the table modules, `Override` and `empty_store()` through a dev-dependency on the owning crate with that feature, with no forgr dependency of their own. A normal build of the owning crate compiles neither forgr nor the fake generator. Call `schema!` inside a module, not at a test file's root next to `use forgr::fake::Override`: at the root, the re-exported `Override` collides with the import and fails with `` error[E0252]: the name `Override` is defined multiple times ``.
- **Published to crates.io** (PR #12, #1; PR #26, #24): the workspace publishes as `forgr-schema`, `forgr-macros` and `forgr`, under the MIT license, on edition 2024 with `rust-version = "1.89"`. forgr's crates.io page is the workspace README. The internal path dependencies are pinned in `[workspace.dependencies]`, so a release moves them with the version. CI runs fmt, clippy with warnings denied, and the tests on Linux, macOS and Windows. Acceptance scenarios run under `cargo test` through rstest-bdd, with one `scenarios!("tests")` runner per crate.
